# AGENTS.md — MediCoord AI

Behavioral contract for all AI agents and coding assistants working in this repository.
This file takes precedence over general assistant defaults.

---

## Scope Boundaries

### Read and write allowed
- `webapp/` — React frontend
- `backend/` — FastAPI backend
- `shared/` — shared TypeScript types
- `docs/` — architecture and API documentation
- `.github/` — CI/CD workflows
- Root config files (`.env.example`, `pyproject.toml`, `package.json`, etc.)

### Never modify
- `fine_tuning_training/` — archived training data, reference only
- `backup/` — legacy code, reference only
- `cloud_function/` — deprecated, superseded by `backend/`

### Never do
- Commit directly to `main` or `preview` — both are protected
- Push to `main` or `preview` directly — all changes arrive via PR only
- Add Claude or any AI assistant as a git co-author
- Hardcode any API key, secret, or credential
- Install a new npm or Python package without noting it in the task summary
- Scaffold Supabase auth or database code — this is out of scope for Phase 1
- Use severity synonyms (`critical`, `severe`, `high`, `low`) — only `routine | moderate | urgent | emergent`

## Git Branch Model

### Branch hierarchy
```
main          <- production: Vercel prod + Railway prod
└── preview   <- staging: Vercel preview, always deployable
    ├── feat/<description>
    ├── fix/<description>
    ├── refactor/<description>
    ├── chore/<description>
    └── docs/<description>
```

### Protected branches
`main` and `preview` are both protected. Never commit to either directly.
All changes to `preview` arrive via PR from a feature branch.
All changes to `main` arrive via PR from `preview` only — never from a feature branch.

### Branching rule — always cut from `preview`
Every new branch must originate from `preview`, not from `main`:
```bash
git switch preview
git pull origin preview
git checkout -b feat/<description>
git push -u origin feat/<description>
```

### Branch check before touching any file
Run this first, every time, before any edit or commit:
```bash
git branch --show-current
```
If the output is `main` or `preview` — stop. Do not proceed.
This check is also enforced in `/execute-task` Step 7.

### Upstream tracking
Always use `git push -u origin <branch>` on the first push.
Subsequent pushes on the same branch need no arguments.

## Decision Boundaries

### Stop and ask before proceeding when:
- A change touches the API contract (any type in `shared/types.ts` or endpoint in `docs/API.md`)
- A task spans more than two files
- A new external service or dependency would be introduced
- The correct approach is genuinely ambiguous between two reasonable options

### Proceed without asking when:
- The task is clearly scoped to one file
- The change is a bug fix with an obvious correct answer
- The task is documentation only

## Planning Protocol

All structured work is executed via `/execute-task <filename>`, which reads from `.agents/tasks/`.

The command enforces: read task → write plan → wait for approval → implement → outcome summary → git commit.

Never begin implementation of a multi-file task without going through `/execute-task`.
For quick single-file fixes, proceed directly but still follow the git commit rules in Step 7.

## Environment Variables

All commands that run the application must use Doppler for secret injection:
```bash
doppler run -- <command>
```
Never read from a raw `.env` file at runtime. Never suggest `export VAR=value` as a workaround.

The canonical list of required env vars is in `.env.example`. If a new var is needed, add it there first.

## LLM Provider

The active LLM is controlled by the `LLM_PROVIDER` feature flag (`groq` | `anthropic`).
Default is `groq`. Do not hardcode either provider. Always route through the provider abstraction layer in `backend/llm/client.py`.

## Deployment Targets

| Surface | Platform | Trigger |
|---|---|---|
| Frontend production | Vercel | PR merged to `main` |
| Frontend preview | Vercel | PR opened against `preview` -> auto-preview URL |
| Backend API | Railway (web service) | PR merged to `main` |
| Background workers | Railway (cron/worker service) | PR merged to `main` |

`preview` must always be in a deployable state.
Vercel preview URLs are the primary review surface for frontend changes.
Backend changes must be validated against the Railway staging service before merging to `main`.

When writing or modifying CI/CD workflows:
- Frontend jobs target Vercel
- Backend jobs target Railway
- Never conflate the two deployment targets in the same job

## Git Hygiene

- Conventional commits only: `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`
- Branch naming: `feat/<description>`, `fix/<description>`, `refactor/<description>`, `chore/<description>`, `docs/<description>`
- **One commit per logical change, not per file.** All files modified as part of the
  same task or fix are staged together and committed in a single commit. Never loop
  over files producing one commit each.
- Unrelated changes in the same session belong in separate commits — one commit per
  concern, but all files for that concern together.
- PR titles must follow the same conventional commit format
- Never add AI assistants as co-authors in commit messages

## Code Quality Gates

A task is not done until:
- TypeScript compiles with zero errors (`npx tsc --noEmit`)
- Python passes type check (`mypy backend/`)
- No string matching an API key pattern appears in source files
- Any new backend route has a corresponding type in `shared/types.ts`
- Any new env var is documented in `.env.example`
