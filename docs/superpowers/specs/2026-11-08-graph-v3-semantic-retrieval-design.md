# Graph v3: graph rebuild and semantic candidate path — Design

Date: 2026-11-08 · Branch: `feat/eval-hardening` · Sprint 23, steps 3–4 (`CHANGELOG.md`, "Sprint 23 — Started") · Status: **draft for approval**

Labels used below: **Decided** = you said so in this conversation. **Proposed** = my recommendation, not yet confirmed by you. **Measured** = a number from our own offline experiments (`backend/scripts/embedding_eval/README.md`). **Cited** = from the research files in `artifacts/`. **Open** = needs a decision before or during planning.

## 1. Intent

Sprint 23's goal is one triage number with an interval that holds up under review, measured in the language guests actually use. Today the graph path does not help lay-language messages: both v1 and v2 score 0/10 on the vocabulary-neutral set because the lookup is a literal substring match (`toLower($text) CONTAINS toLower(d.term)`), and the v2 graph (31,327 concepts, 50,351 IS_A edges, deleted when AuraDB Free paused) had blanket depth-4 expansion over broad anchors. This spec does two things together:

1. **Rebuild the graph** so it is small, bounded and clinically cohesive, with lay-language descriptions as a first-class layer.
2. **Add one semantic candidate path** to the request path so lay messages find the right anchors, with the existing lexical lookup kept and a safe fallback.

Success is judged by the sprint's line in the sand: publish under-triage for `off`, `static` and `v3` on both vignette sets with intervals; if `v3` does not beat `off` beyond the paired interval on the lay set, `off` stays the default and the negative result is published.

## 2. Evidence this design rests on

- **Measured, retrieval** (gold anchor in top 5, SNOMED anchor descriptions only; "valid" = a blind labeler agreed with the gold anchor):

| | Substring today | BioLORD-2023 | bge-small | SapBERT | S-PubMedBert-MS-MARCO |
|---|---|---|---|---|---|
| Author-written set (150), hit@5 (substring: any match) | 4% | 92% | 78% | – | – |
| Independent valid set (469), hit@5 (substring: any match) | 5% | 83% | 65% | 52% | 50% |
| Single message, torch fp32, 8-core laptop | – | 57.8 ms | 14.6 ms | 53.2 ms | 47.3 ms |

- **Measured, descendants:** adding SNOMED descendants at depth ≤2 lowered hit@1 for every model and BioLORD's hit@5 by about 8 points. At depth ≤2, 735 of 9,103 concepts (8.1%) are reachable from more than one anchor (55 of 2,638, 2.1%, at depth ≤1). Anchor size is very skewed: median 15 concepts, 12 anchors above 200, largest 1,389 ("Other skin conditions").
- **Measured, lay phrases** (1,487 generated, 48% labeler-confirmed): BioLORD barely changes; bge-small gains (hit@5 on the independent set 65% → 75–80%); the substring lookup roughly doubles but stays at 10–17%.
- **Cited (audit and design brief, `artifacts/2026-11-04-*`):** root causes are blanket depth (`MAX_SEED_DESCENDANT_DEPTH = 4`), broad anchors, uncurated keyword seeds, ingestion-down/retrieval-up mismatch; per-anchor `max_depth` is applied only at query time. The brief recommends SapBERT; our measurement ranks SapBERT below BioLORD and bge-small on lay sentences, so this spec replaces that recommendation.
- **Cited, research** (`artifacts/research/2026-11-08-*`): short-message input and abstention practice; AuraDB Free limits (200k nodes/400k relationships, deleted after 30 days inactive); Railway self-host about $40.75/month for 1 vCPU/2 GB/5 GB.
- **Caveat on all of the above:** the queries are synthetic, and the model ranking is more trustworthy than the absolute levels.

## 3. Goals, non-goals, anti-goals

**Goals**
1. A rebuilt graph that meets the structural checks in §10 and covers all 154 anchors.
2. A lay-description layer (generated, labeled, reviewed, stored with provenance) that works with either embedding model.
3. A semantic candidate path behind a feature flag, with lexical fallback, an abstention rule and bounded cost.
4. An offline harness (already committed) and an end-to-end comparison that decide, on latency, CPU and quality, which embedding model ships.

**Non-goals**
- Multilingual support (English only for now). pgvector. Step 2 hardening (spend cap, breaker on LLM providers; runs in a separate session). The paid pilot and full run (steps 5–6). The README rewrite (step 7).
- Changing severity classification: it stays the LLM's job.
- Replacing the IS_A traversal, red-flag collection or the `GraphContext` contract.

**Anti-goals** (a technically working result that still counts as failure)
- A semantic path that makes the live turn slower or less available than the lexical one (§8.6).
- A path that returns a red-flag block for off-topic messages (§8.5).
- Numbers that come from a test set generated by the same model that wrote the lay descriptions.
- A vector index that silently disagrees with the live graph or model (§8.3).

## 4. Decisions

**Decided**
- English only; non-commercial use for now (a cc-by-nc model is acceptable for experiments; BioLORD still needs UMLS/SNOMED licence compliance).
- BioLORD-2023 is the working choice; a later end-to-end test of **BioLORD-2023 and bge-small** decides what ships, on latency, CPU cost and quality.
- The lay-description layer is first-class and model-agnostic (it is what makes bge-small competitive).
- Gates: headline = `v3` under-triage below `off` beyond the paired interval on the lay set; co-gates = retrieval hit@5 (lower confidence bound ≥ 75%), abstention false-match rate, p95 latency and CPU within budget; structural checks are advisory (§10).
- Lay descriptions are generated by an LLM and stored with provenance; the model is set by env var.
- The vector artifact is **built at deploy on the python-api service's attached volume** (see §8.8); the pre-deploy command cannot be used for it.
- Hosting: **AuraDB Free with the existing keep-alive**; a snapshot is taken **automatically at graph deployment** so a restore needs no rebuild (§9). Railway self-hosting is not part of this plan.
- Runtime embedder = **ONNX Runtime int8**, initialised with explicit thread limits, no idle spinning and a warm-up before it is marked ready (§8.7–8.8).
- Approved as proposed: the numeric starting budgets (§10), the lay-description data file path and review rule (§7), the provider value `neo4j_semantic` (§5.2), and a final decision test set from a third generator (§7).

**Proposed** (please confirm or change)
- Add **one** semantic candidate path; keep the lexical lookup as an exact-match path and as the fallback; a lexical exact hit outranks a semantic-only hit.
- Vectors held **in the API process** as one matrix (about 30–60 MB); pgvector deferred; Neo4j's native vector index noted as an alternative.
- Embedding input = the **current message** by default; concatenation and per-message fusion tested offline on the step 5 transcripts.
- One **primary anchor per concept** for the retrieval index (shortest IS_A path, ties flagged), all IS_A edges kept in the graph.
- Broad anchors: a **rule** flags them (more than 200 concepts at depth ≤2, plus catch-all names), then a manual review of the flagged ones only.
- **Index depth 1** by default, depth 0 for the catch-all anchors, deeper only as a documented per-anchor override.

## 5. Architecture

### 5.1 Build pipeline (offline, run deliberately)

```
anchor_mapping.py (154 reviewed anchors)  ──┐
SNOMED CA RF2 (descriptions, IS_A)          ├─►  1. select concepts (per-anchor depth, blocklist, primary anchor)
v1 aliases (symptom_triage_data.json)       ──┘          │
lay_descriptions.json (reviewed phrases)  ──────────────►├─►  2. load Neo4j: Layer 1 concepts + descriptions (incl. kind:"lay"),
CTAS red flags / follow-ups  ───────────────────────────►│        Layer 2 red flags + follow-ups (scoped per anchor)
                                                          ├─►  3. quality checks (§10 advisory metrics)
                                                          └─►  4. embed all description rows per model → vector artifact + manifest
```
- Idempotent: wipe and reload; reruns with changed anchor scope leave no orphans.
- Seeds are the 154 reviewed anchors only (no keyword seeds from `complaint_seeds.py`); top-level groupers (`404684003`, `95320005`, `66091009`, …) are blocked.
- `load_rf2.py` must apply each anchor's `max_depth` at ingestion; today it uses the global constant 4 and ignores the field.
- `FollowupQuestion` is scoped per `(anchor_id, text)`, not by global text, and `RedFlag` stays keyed per anchor.

### 5.2 Request path (per user turn, inside `Neo4jSnomedProvider._lookup`)

```
all_text ──► [lexical candidates]  (existing Cypher CONTAINS, exact hits)
        └──► [semantic candidates] embed(current message) ──► exact scan over description vectors ──► top-N rows ──► concept ids + scores
                                                                │ timeout / breaker open / index stale ──► skipped for this request
union ──► existing IS_A traversal to anchors (batched by max_depth) ──► red flags + follow-ups
      ──► abstention check on the semantic part ──► rank (lexical exact first, then semantic score; CTAS level for red flags)
      ──► GraphContext
```
- The `GraphContextProvider` contract is unchanged, including "never raises": any failure degrades to the lexical result, then to `matched=False`.
- Only the candidate-generation step changes. Specificity today is "longest matched term"; for semantic candidates it is the similarity score.
- Release control: a new `GRAPH_RAG_PROVIDER` value (proposed name `neo4j_semantic`); `off` stays the default; `neo4j` (v2) is untouched and the evaluation legs are `off`, `static`, `v3`.

### 5.3 Components (dependency rule: details depend on policies)

| Component | Responsibility | Depends on |
|---|---|---|
| `Embedder` (interface) | text → vector | nothing |
| `OnnxEmbedder` | tokenizer + ONNX session, model name, pooling, prefix, max length from config | onnxruntime, tokenizers |
| `SemanticIndex` | loads the artifact, validates the manifest, `search(vector, n)` → rows | numpy |
| `SemanticCandidateSource` | message → candidates, applies deadline, breaker and bulkhead | `Embedder`, `SemanticIndex` |
| `Neo4jSemanticProvider` | composes lexical and semantic candidates into `GraphContext` | existing provider logic |
| `main` / wiring | picks provider, model and artifact from env | all of the above |
Only wiring knows concrete classes; the offline harness imports the same scoring helpers.

## 6. Graph build rules

- **Depth:** index depth 1 by default; per-anchor override in data, not code. Query-time `max_depth` (anchor mapping) is unchanged.
- **Polyhierarchy:** each concept is assigned one primary anchor for the index (shortest IS_A path; ties flagged for review). A build check reports concepts reachable from more than one anchor; at depth ≤1 only 2.1% were.
- **Broad anchors:** flagged by the rule above (12 anchors at depth ≤2 in current data); flagged anchors use depth 0–1 and rely on lay descriptions; only those are reviewed manually.
- **Caps (advisory):** in-degree and out-degree limits per the audit's starting values (§10).
- **Budget:** well under 50,000 nodes / 75,000 edges (current depth ≤2 concept count is 9,103 plus descriptions and Layer 2).

## 7. Lay-description layer

- **Generation:** `gen_lay_descriptions.py` (committed after approval), model from `EVAL_GEN_MODEL`, 9–10 phrases of 2–8 words per anchor; cost about $0.06 per full run (Measured).
- **Blind label check:** shuffled before labeling; each phrase records `agree_top1`/`agree_top3`. Measured: 48% top-3, 36% top-1, so most phrases are ambiguous on their own — the check is a quality signal, not a gate by itself.
- **Status per phrase:** `generated`, `confirmed` (labeler agrees), `rejected`, `approved` (human). Phrases with fewer than 2 words are dropped.
- **Inclusion rule is a build setting** (`all` / `confirmed` / `approved`), chosen with the final test; both settings are in the manifest.
- **Coverage:** 6 anchors currently have no confirmed phrase; a second pass with a cue-preserving prompt (about $0.02) closes this. The human spot-check concentrates on the emergent anchors.
- **Storage:** source of truth is a reviewable data file in the repo, proposed `backend/scripts/snomed_ingest/data/lay_descriptions.json`; the build loads approved phrases as `Description` nodes with `kind: "lay"`, `source` and `status`, attached to the anchor concept, so the lexical and semantic paths both see them.
- **Independence rule:** descriptions and the final decision test set must come from different generators. The hand-written author set stays as the clean hold-out; the final comparison should add a set from a third generator.

## 8. Semantic path

### 8.1 Model configuration
Model id, pooling, query prefix, max length and ONNX path come from config; the index records the same. Swapping BioLORD and bge-small is a config change plus an index rebuild.

### 8.2 Index artifact
One row per description (text, concept id, primary anchor id, kind). Format: a float32 matrix plus an id file. Cosine via normalized dot product, exact scan (about 20K rows, a few milliseconds by estimate).

### 8.3 Manifest and staleness
The manifest records model id and dimension, pooling and prefix, lay inclusion rule, row count, a hash of the description rows and the graph build id. At startup the provider compares it with the live graph; a mismatch logs and disables the semantic path (lexical only). The index is rebuilt whenever the graph or the model changes.

### 8.4 Embedding input
Default: the current message only. The provider today joins the message with recent user messages; the offline experiment on step 5 transcripts compares (a) current only, (b) concatenation, (c) per-message embeddings fused by max per anchor. An LLM rewrite is rejected (adds an LLM call to the path).

### 8.5 Abstention
- An embedding search always returns a neighbour, so a rule is required: accept the semantic part only if the top anchor score passes a threshold **and** the gap to the second anchor passes a margin (research: raw top score is a weak signal; the gap is better).
- Thresholds are per model and per index; calibrated on a validation split of a negative set (about 100–200 messages: off-topic chat, health-admin questions, symptoms outside the 154 anchors, near-misses, empty or very short input, injection-style strings), reported on a held-out test split with both in-scope hit rate and out-of-scope false-match rate.
- The score and gap thresholds are set after the negative set exists; the false-match target is in §10.

### 8.6 Stability (release-it lens)
- A per-request deadline on the embed step (configurable; **Open:** value to be set from the measured p95 on the production box). On timeout the semantic part is skipped for that request.
- A circuit breaker on consecutive timeouts/errors (half-open probes); a tripped breaker is expected behaviour, alert when it stays open.
- A bulkhead: inference runs on a bounded worker pool so it cannot starve other work; the pool size follows the core count.
- Metrics: semantic used / skipped (timeout, breaker, stale, abstained), embed duration, plus the existing `GRAPH_LOOKUP_DURATION`. `/health` reports index loaded and manifest valid.
- Capacity: Sprint 22 measured about 35 turns/s on one box at about 16 ms of API CPU per turn. The semantic step must be load-tested; the capacity co-gate in §10 follows from that.

### 8.7 Runtime packaging
The API image gets onnxruntime and tokenizers, not torch. Models are exported **offline** to int8 ONNX (torch is used only there), parity-checked against the torch model (embedding cosine and the hit@5 delta on the harness), and copied **once** to the python-api volume (Railway CLI or SFTP/SCP, per its volume docs). Their checksums go in the manifest. Nothing is downloaded from Hugging Face at runtime. Any new package goes into `requirements.txt` and is called out in the task summary.

### 8.8 Runtime initialisation (ONNX Runtime) — avoiding all-core use and cold starts
*Cited (onnxruntime.ai thread-management and quantization docs):* with `intra_op_num_threads` unset the intra-op pool is sized to the number of **physical cores**; the inter-op pool exists only in parallel execution mode; the default `execution_mode` is `ORT_SEQUENTIAL`; idle-thread spinning is **on** by default (`session.intra_op.allow_spinning`, `session.intra_op.spin_duration_us` control it); S8S8 with QDQ is the first-choice int8 format; on x86-64 AVX2/AVX512 **without VNNI**, U8S8 can saturate (use `reduce_range` or U8U8); quantization is "not a loss-less transformation", so compare fp32 and int8 outputs. *Lead, not confirmed:* a dotnet/machinelearning PR states that in Docker ONNX Runtime counts the host's cores, not the container's allocation; the docs say nothing on containers or cgroup quotas, so the thread count must be set explicitly.

Initialisation recipe (proposed; values are config):
1. **One** `InferenceSession` per process, created at startup and reused for every request.
2. Threads set explicitly: `intra_op_num_threads` from `EMBED_THREADS` (default **1** on the 1 vCPU box), `inter_op_num_threads=1`, `ORT_SEQUENTIAL`. The tokenizer library gets `TOKENIZERS_PARALLELISM=false` and `RAYON_NUM_THREADS` equal to the same value (estimate from library practice; verify).
3. `session.intra_op.allow_spinning=0` so idle threads do not burn CPU between turns; measure the latency cost before keeping it.
4. **Warm-up before ready:** run a few inferences with representative message lengths at startup. The semantic path stays disabled and `/health` reports "warming" until done. Cold-start effects are not covered by the docs I read, so the first-call vs steady-state latency is measured in the plan, not assumed.
5. **Bounded concurrency:** inference runs on a worker pool of `EMBED_THREADS` workers behind a queue with the request deadline (§8.6), so concurrent turns wait or skip instead of oversubscribing the CPU.
6. Input handling: max length 64 tokens, batch of one, no padding beyond the message.
7. **Quantization matched to the CPU:** read the Railway box's CPU flags (`/proc/cpuinfo` on the service) and export the int8 variant that suits them (VNNI: S8S8 QDQ; otherwise `reduce_range` or U8U8); a model quantized for the wrong instruction set can be slower than fp32. The parity test is the gate. **Open:** the Railway CPU flags are not yet known.

### 8.9 Index build and distribution (decided: build at deploy on the python-api volume)
*Cited (Railway docs):* a pre-deploy command runs in a **separate container with no volume mounted** and its filesystem changes are not persisted, so volume work belongs in the **start command**; a service supports one volume and **no replicas**; redeploying a service with a volume causes a **brief downtime**; the Hobby volume limit is 5 GB; non-root images may need `RAILWAY_RUN_UID=0` for volume access. The repo does not record the existing volume, so its mount path is confirmed in the plan.

Design:
- The start command runs `ensure_index` and then starts the API. `ensure_index` compares the volume's manifest (§8.3) with the live graph hash and the model/lay settings. **Match: exit at once** (normal restarts cost nothing).
- **Missing or stale:** the API still starts immediately, in lexical-only mode, and a **separate low-priority build process** (`EMBED_THREADS` threads) embeds the description rows with the same ONNX int8 session used for serving, writes to a temporary directory on the volume, then **atomically renames** it into place. A blocking build before start was rejected: a first build of about 20K strings on one vCPU takes minutes and could trip the healthcheck.
- The API loads the new index when the manifest changes (checked on the next restart or by a periodic check); `/health` reports `building`, `ready` or `stale`.
- The build uses the serving runtime, so vectors and queries share the same numerics.
- A failed or partial build never replaces a good index.
- Trade-offs accepted with the volume: single replica for python-api and a brief downtime on each redeploy (already the case if the volume exists; Hobby allows one replica per service anyway).

## 9. Hosting

- **Decided:** AuraDB Free for the graph (small and regenerable), kept alive by the existing `/health` ping. *Cited (Aura FAQ):* 200k nodes / 400k relationships, data not queryable while paused, Free instances without activity for 30 days are deleted.
- **Snapshot at graph deployment (decided):** the build's last step takes an on-demand snapshot **after the verify step passes**, so a failed build can never replace the only good snapshot. Restoring then uses Aura's snapshot restore and needs no rebuild.
  - *Cited (Aura docs):* on-demand snapshots are "the only snapshot available for Free instances", triggered with the **Take snapshot** button; the Aura CLI has `aura-cli instance snapshot create --instance-id …` and restores with `aura-cli instance overwrite DESTINATION --source-instance-id … --source-snapshot-id …`; a snapshot can only be taken while the instance is running. **Not established by the docs:** that the CLI works on Free, how many Free snapshots are kept (the Free row is N/A; one is likely), whether Free snapshots can be restored or exported, and what happens to snapshots when a Free instance is deleted.
  - **Open (first tracer run):** try the CLI snapshot on the Free instance. If it works, the build does it automatically; if not, the deploy checklist includes the console button as a manual step, and the build prints a reminder. The build scripts plus the committed lay data file remain the ultimate backup.
- Vectors stay in the API process (and on the volume, §8.9). Whether Aura Free supports a native vector index is not established; the design does not need it.

## 10. Evaluation and gates

**Headline (fixed):** end-to-end under-triage of `v3` below `off`, beyond the paired interval, on the lay set (Sprint 23 steps 5–6).

**Co-gates**
1. Retrieval screen (step 4): hit@5 on the independent valid set with the lower 95% bound ≥ 75% (also report hit@1); if the screen fails, stop before the paid pilot and record why.
2. Abstention: out-of-scope false-match rate ≤ 5% (approved starting value, unsourced), with the in-scope hit rate reported alongside; thresholds calibrated per §8.5.
3. Latency and CPU: p95 added latency ≤ 120 ms and single-box capacity ≥ 15 turns/s (approved starting values, unsourced), revisited once the ONNX int8 timings on the Railway box type exist.

**Advisory build-health checks** (reported, not blocking; starting values from the audit, unsourced): max/median degree under 50×; IS_A in-degree ≤ 50; ASKS in-degree ≤ 5; HAS_RED_FLAG out-degree ≤ 20; 154/154 anchors loaded with at least one descendant or lay description; measured component count (the audit's "≥10 components" is revisited after the first measurement, since no count was ever taken on the old graph); under 50K nodes / 75K edges.

**Final decision test (BioLORD vs bge-small):** configurations compared on latency, CPU and quality: BioLORD + lay, bge-small + lay, and BioLORD without lay as a control. Quality uses the held-out sets; latency and CPU use the production box type with ONNX int8.

## 11. Testing

- Unit: scoring helpers (exists), candidate fusion and ranking, abstention rule, manifest check, breaker/deadline behaviour with a fake embedder.
- Integration: provider with a fake Neo4j client and fake embedder covering normal, timeout, breaker-open, stale-index and empty-embedding cases.
- Build: quality queries (§10) as an automated report; idempotent wipe/reload test on a small anchor subset.

## 12. Cost notes
Lay descriptions about $0.06 (done once, regeneration cheap); test query sets about $0.04; embedding the descriptions is a one-time local CPU job; no paid embedding API is used or proposed. Any new paid call is flagged with an estimate before it runs.

## 13. Calls made by the builder of this spec (for you to check)
1. The semantic path ships behind its own provider value, leaving v2 untouched.
2. Lexical exact hits outrank semantic-only hits.
3. Threshold on both the top score and the gap.
4. ONNX int8 in the API, torch only offline.
5. Lay phrases of 2–8 words, minimum 2 words, to keep the substring path safe.
6. Starting values for the false-match rate and latency/capacity budgets are unsourced (approved by you as starting points).
7. The index build runs as a background process at start, not blocking the API, to avoid healthcheck timeouts.
8. Quantization is chosen from the target CPU's flags, with a parity test as the gate.
